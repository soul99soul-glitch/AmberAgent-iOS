## S1: production reachability confirmed, baseline-only fix is insufficient

- Chat/Session/ChatConversationMutations.swift:777-821 starts independent delete/select Tasks. No branch mutation owner is reserved, and isGenerationActive stays false during these ordinary storage actions. Multiple variant buttons / context-menu delete operations can therefore enter while another disk save is pending. sendMessage also has no pending-branch guard.
- Chat/Storage/IOSConversationBranching.swift reads currentConversation, transforms the full nodes snapshot, then awaits persist. IOSConversationStore.persist:1318-1327 increments writeSequence and awaits storage.saveConversation; currentConversation is not advanced until the branch caller resumes. KMP JsonConversationStorage.saveConversation:169-175 explicitly switches file work onto Dispatchers.Default while holding its operation mutex, allowing Swift MainActor to receive the next user operation.
- KMP mergeMessageWriteWithExistingMetadata:349-378 merges metadata only; incoming messageNodes remain authoritative. Two successful snapshots based on [A,B,C] can therefore save [B,C] then [A,C], resurrecting A. The metadata mutex does not merge node edits. changedDuringSave only reloads whichever full snapshot won the disk write; it cannot recover the lost mutation.
- Important correction to initial repair recommendation: simply capturing existing writeBaseline before the branch read is insufficient for the actual in-flight window. First operation has already advanced sequence from 0 to 1, but currentConversation still contains the original nodes. A second operation reads that old currentConversation and captures sequence 1, so its baseline is still accepted even though its nodes are stale. A test that pauses only beforePersistForTesting (before sequence reservation) proves only the easier stale-read window.
- Minimal viable options: (1) reserve a branch-mutation owner synchronously at the user action boundary and block conflicting branch/send operations with visible state until persistence settles, covering all branch starters and preserving per-conversation ownership; or (2) serialize node transformations inside the conversation store before reading their source snapshot, matching requests by original node identity so queued deletes do not shift index targets. Choose one existing-owner implementation, not a general retry or storage framework. If store writes are serialized, include save(messages:) overlap in the design or explicitly reject its conflicting owner.
- Required regression: pause after first sequence reservation while actual storage save is suspended, trigger second user branch action; verify no falsely successful lost mutation. Cover delayed branch versus send/save, node-index shifts if queueing, conversation switches, and persisted restart state.

## S2: accepted exactly as reported

DocumentAccessStore.trailingInt:805 calls name.reversed().prefix(isNumber). Every standard PPTX slide path ends .xml, so reversed starts l and returns zero. entryNames returns arbitrary ZIP central-directory order sorted by equal zero keys. readPptxPreview:508-519 then labels that arbitrary sequence [Slide 1], [Slide 2], etc. Numeric ordering is explicitly promised in the code and affects every supported import route. Strip the path extension before extracting trailing digits and use the existing public stored-ZIP import seam with slide1, slide10, slide2. PowerPoint relationship/custom order is distinct unsupported format work; do not broaden this fix.

## CRED-1: proposal leakage and invalid selection confirmed

- IOSSharedSettingsStore.restoreSnapshot:290-307 rejects on a required Keychain write, rolls back prior writes, and preserves snapshot/JSON/revision. upsertProviderChatModel:886-887 discards that Bool and returns the provider from merged, which includes the proposed model and plaintext runtime header. This is a leaked uncommitted proposal, not a runtime snapshot leak to a provider request.
- ProviderDetailView.saveModelDraft:1347-1384 uses that returned proposed model as success. For manual CHAT add, shouldSelectChat is true and selectCurrent:1407-1409 calls selectChatModelAsDefault with its new UUID. The old snapshot contains no new model/header, so this later selection can succeed without retrying the rejected new credential; it commits the invalid UUID and can clear credentialPersistenceError. KMP setChatModelId validates UUID syntax only. Editor then closes via true.
- By-design check: updateProviderApiKey already guards restoreSnapshot and returns from committed snapshot. The rejecting transaction contract is explicit. A successful return from uncommitted merged violates it.
- Minimal repair: return nil on failed restoreSnapshot and fetch the provider from snapshot after success. saveModelDraft must show the existing credentialPersistenceError and return false, preserving the draft and selection. Same contract for directly involved model helpers prevents equivalent catalog success claims. No fallback store/retry needed.
- Regression: injected sensitive model-header write rejection must leave snapshot/persisted JSON/revision/current UUID unchanged, return nil and retain error. UI regression must retain editor + draft, and must not call default selection after rejection.

## CRED-2: precommit deletion remains destructive on rejection

- removeProviderChatModel:906-909 deletes actual generic refs before restoreSnapshot. updateProviderChatModels:778-784 repeats the same pattern. Both call IOSCredentialSideTable.delete directly and bypass the store injected deleteCredential.
- Generic path construction at IOSCredentialRedactor:263-274 includes stable identity plus array index at each level. Removing A before B shifts B to a new model index, requiring a write of its retained sensitive header to the new ref. KMP removeProviderChatModel uses filterNot (755-769), so this shift is guaranteed for a following model. updateProviderChatModels can also reorder nonchat/chat rows and introduce migration writes.
- If that required write fails, restoreSnapshot rolls back only writes made within itself. A's deleted refs cannot be restored because they were removed before entry. The in-memory old snapshot still contains A raw credentials, but the old masked JSON still points at deleted refs; a fresh store rehydrates A to empty string (IOSCredentialRedactor:185-186). Thus the report's restart credential-loss impact is correct. It is not immediate in-memory A loss, and the report should preserve that distinction.
- Successful restoreSnapshot already deletes obsolete refs after snapshot + JSON commit (312-315), so the premature loops are redundant. Remove them, guard the returned Bool, return committed snapshot, and have delete/catalog call sites stop follow-up state changes and display failure.
- Regression: use unique actual Keychain refs for the red test because direct deletion bypasses injected closures, or otherwise exercise the concrete deletion path through an existing seam without asserting only the fake map. Reject the shifted B write, verify old JSON + both headers survive a fresh store; also verify successful removal deletes A refs and migrates/preserves B. No new keychain abstraction is necessary.
