# Credentials / backup read-only audit

Scope: current working tree, including untracked Settings/Providers split files. Read `iosApp/AGENTS.md`. No source edits, builds, or tests were performed. Findings were rechecked against production callers, the failure behavior of `restoreSnapshot`, and KMP mutations. Two confirmed credential-transaction findings are ready for targeted reproduction and repair.

## CRED-1 — [P1] Failed model credential persistence is returned as a successful model mutation

- Primary location: `iosApp/iosApp/IOSSharedSettingsStore.swift:886`–887 (`upsertProviderChatModel`). It ignores the Boolean returned by `restoreSnapshot(merged)` and returns a provider from the uncommitted proposal.
- Production entry: provider settings model editor -> `ProviderDetailView.saveModelDraft`, `iosApp/iosApp/ProviderDetailView.swift:1347`–1384. The editor exposes custom headers, and its Save button dismisses when `onSave` returns true (`iosApp/iosApp/Settings/Providers/ProviderDetailComponents.swift:242`–243).
- Trigger: create or edit a model with a sensitive custom header, such as Authorization, while the corresponding Keychain store fails. Unlike an ordinary unchanged setting save, this necessarily introduces or changes a credential value.
- Failure chain: `restoreSnapshot` at `IOSSharedSettingsStore.swift:295`–307 returns false, preserving the previous snapshot and persisted settings. `upsertProviderChatModel` still returns `merged`; `saveModelDraft` then finds the proposed model and closes the editor. For a newly added CHAT model, `shouldSelectChat` is true (1340), so `selectCurrent` (1407–1409) can also persist the UUID of the model that never committed. The current chat selection then resolves to no model (`core/types/src/commonMain/kotlin/app/amber/core/settings/Settings.kt:490`–491).
- Observable impact: credential/model edits disappear despite successful dismissal; a failed manual add can leave chat with an invalid selected model until the user selects an existing model.
- Second check: this is not a best-effort/by-design save. `restoreSnapshot` deliberately rejects the whole settings commit with `credentialPersistenceError`; the already-fixed provider API-key method at 679–684 guards that result and returns the actual snapshot. The model path fails to follow that contract.
- Smallest reproduction seam: reuse `FailingSettingsCredentials` in `IOSSharedSettingsStoreProvidersWriteBackTests`. Add a provider successfully, set rejection for a new model Authorization header value, call `upsertProviderChatModel`; assert result is nil, snapshot/persisted JSON/revision stay unchanged, and error is available. UI coverage should confirm failed Save retains the editor and draft, shows the error, and does not change the selected model.
- Smallest repair: guard `restoreSnapshot(merged)` and return nil on failure; return the committed provider from `snapshot`. At the model editor call site, turn nil plus `credentialPersistenceError` into its existing save-failure alert and return false. Apply the same return-value contract to credential-bearing model mutation helpers involved in this phase, without adding retries or fallback storage.

## CRED-2 — [P1] Model removal deletes existing Keychain refs before the settings transaction commits

- Primary locations: `iosApp/iosApp/IOSSharedSettingsStore.swift:906`–909 (`removeProviderChatModel`) and 778–784 (`updateProviderChatModels`). Both delete model credential refs before calling `restoreSnapshot`.
- Production entries: provider model list Delete -> `ProviderDetailView.deleteModel`, `iosApp/iosApp/ProviderDetailView.swift:1430`–1439; catalog replacement -> Antigravity callback at `ProviderDetailView.swift:177`, and `provider_refresh_models` with `mode=replace_chat` at `IOSProviderConfigToolService.swift:397`–398.
- Trigger: a provider has at least two models A and B with sensitive custom headers; remove A before B in the list (or replace the catalog to drop A). Generic refs contain array indices (`IOSCredentialRedactor.swift:263`–274), so B's new position requires a new Keychain ref. Reject that required write.
- Failure chain: A's refs are deleted immediately; then `restoreSnapshot` attempts to migrate B's ref and fails. Its rollback only covers writes it made after entry (`IOSSharedSettingsStore.swift:290`–307), so it cannot restore A's prior deletion. Snapshot and persisted JSON still contain A with its mask sentinel. On a fresh store load, A's missing generic ref rehydrates to an empty string (`IOSCredentialRedactor.swift:185`–186).
- Observable impact: a rejected delete/catalog update permanently loses the retained model's old custom credential after restart. The deletion method also returns the uncommitted provider, so callers cannot distinguish the failed operation.
- Second check: cleanup is already owned by the successful transaction: `restoreSnapshot` commits JSON/snapshot at 312–313, then deletes `previous.values.keys - proposed.values.keys` at 314–315. That includes the removed model's generic refs, so the earlier model-specific deletion is both premature and redundant. No compensation or new storage layer is required.
- Smallest reproduction seam: use an isolated UserDefaults suite and credential map with injected load/store/delete closures. Seed A and B with distinct sensitive custom headers, then reject the new indexed ref needed by B and remove A. Assert failure returns nil; A/B and persisted JSON remain unchanged; restart retains both headers. Current premature deletion calls `IOSCredentialSideTable.delete` directly, bypassing the injected deleter; either use uniquely scoped actual Keychain refs for the red test, or first route the existing direct deletion through the already-existing injection seam so the test observes it. The final repair removes the premature calls entirely.
- Smallest repair: remove the pre-commit generic-ref deletion loops in both methods, relying on `restoreSnapshot` for post-commit cleanup. Guard its Boolean, return the provider from committed `snapshot`, and make production callers display the existing persistence error without changing defaults or reporting deletion success. Regression-check successful deletion still removes all removed-model refs and preserves surviving model headers after restart.

## Exclusions / limits

- Backups deliberately redact credentials before encryption and rehydrate from the local side table; cross-device re-entry is intentional, not itself a defect.
- Runtime mask leakage is already addressed by the generic rehydrator replacing missing refs with empty strings.
- The model-fetch UI captures its provider and headers, cancels old work, and checks request identity before publishing results; no stale-provider overwrite was established in that UI path.
- Current-model deletion intentionally asks the user to choose another model, per its explicit alert; no separate dangling-default finding was raised for that normal successful-delete behavior.
- No simulator, Keychain failure injection, or device validation was executed in this read-only audit. The findings above are production-reachable source proofs with narrow reproduction seams, not claims of completed test execution.
