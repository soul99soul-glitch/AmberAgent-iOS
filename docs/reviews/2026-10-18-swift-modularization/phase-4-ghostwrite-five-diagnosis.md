## Most useful next discriminator

The first-chapter collect returns with a rotated chapter-2 plan. `runGhostwriteBatch` then immediately refreshes and enters `runOneGhostwriteChapter` for chapter 2 (`NovelSessionGhostwriteBatch.swift:428–520`). With no third adapter request, the remaining likely boundary is **before** the second model invocation: `obtainGhostwriteCandidate` calls `start`, and a failed `start` throws `NovelError.invalidInput(operationErrorMessage)` (`NovelSessionGhostwriteChapter.swift:~553–570`). `startBlockerMessage` can reject a still-draining `terminalAwaitingRefresh`, a busy workspace, or a still-active durable run (`NovelSessionRunLifecycle.swift:242–285`). A fast scripted first chapter can leave a durable candidate available before its UI consumer finishes the terminal FIFO drain (`NovelSessionStreamingPresentation.swift:~329–413`); the current candidate wait returns on availability alone (`NovelSessionGhostwriteChapter.swift:~602–638`). This is a **timing hypothesis**, not an established cause. A domain start error before reaching the adapter is also compatible with the two-request count.
