# Foreground resume / late detach: read-only diagnosis

## Observed result and baseline

- Main r3 `NovelGenerationLifecycleTests/testForegroundResumeKeepsReplacementStreamWhenDetachReturnsLate` failed in 1.07 s. `NovelGenerationRecoveryTests.swift:283` did not observe `adapter.resumeRequests.count == 1` within the test's existing 1-second `eventually` gate. At line 295, the next subscriber event was not `.delta("后段")`. The r3 xcresult detail does not record the actual request count or next event, so the second assertion is not independent proof that the late `detach` removed a replacement stream.
- The test method body is byte-for-byte equal to the migration source at `/tmp/amber-phase4-source-baseline/files/iosApp/iosAppTests/NovelGenerationLifecycleTests.swift:1045`. The test adapter's `detach`, `resume`, and `yieldResumed` bodies also match. Production bodies for `resumeDetachedGenerationRuns`, `resumeAllDetachedGenerationRuns`, `resumeDetachedRun`, `detachResumableRunForBackground`, `installModelStream`, `consumeModelEvent`, `interruptForBackground`, `recoverGenerationStateIfNeeded`, `modelStreamEnded`, and `flushRecoverySidecar` match their pre-split baseline exactly. This is not a changed-body Phase 4 regression.
- r2 passed the same case; r3 failed. That difference is consistent with a scheduling-sensitive race, but is not by itself proof of the precise interleaving.

## Reachable competing interleaving

1. The first response frame broadcasts `.delta("前段")` before its awaited sidecar flush finishes (`NovelGenerationStream.swift:714-748`). The test consumes this presentation event and starts background interruption; `detachResumableRunForBackground` forces the sidecar flush, sets `runtime.isDetachedForBackground = true`, then awaits adapter `detach` (`NovelGenerationStream.swift:573-608`).
2. The scripted adapter closes the initial stream *before* blocking its `detach` return (`NovelGenerationLifecycleTestSupport.swift:570-580`). Its old `installModelStream` consumer can therefore exit and queue `modelStreamEnded` while the adapter reports `detachIsBlocked == true`.
3. Foreground `resumeDetachedGenerationRuns` sees the detached runtime. `resumeDetachedRun` changes `isDetachedForBackground` to `false` **before** awaiting `beginRecoveredBackgroundLease` and before invoking `durableRunner.resume` (`NovelGenerationStream.swift:342-369`). At that suspension, the old consumer's `modelStreamEnded` can run. Its only guard is `terminalClaim == nil` and `isDetachedForBackground != true` (`NovelGenerationTerminal.swift:6-20`); it does not identify which model stream ended. It can incorrectly call `failRun(...stream_ended)` for the old, deliberately closed stream.
4. If that terminal claim is installed before the resumed lease returns, `resumeDetachedRun`'s post-lease guard rejects the run and never calls the adapter's `resume`. The test then sees zero resume requests and a failed/interrupted event instead of `.delta("后段")`. If the old consumer ends before the flag flips, the guard suppresses it and the test passes. The exact request count and event in r3 remain unrecorded, so this is a concrete reachable explanation, not yet a proven r3 event trace.
5. A related late completion is possible after a successful `durableRunner.resume`: `installModelStream` cancels the previous `modelTask`, whose `modelStreamEnded` can still run after the replacement is installed while `isDetachedForBackground == false`. The same missing stream-owner identity can terminalize the replacement. The existing after-detach guard protects `detachResumableRunForBackground` from canceling the replacement, but does not protect `modelStreamEnded` from an old consumer.

## Decision boundary

- Do not increase `eventually` timeout, weaken assertions, or infer a fixture-only failure. The test intentionally forces a late detach and the method/adapter are unchanged from pre-split. The production `modelStreamEnded` guard can misattribute the end of an old local stream to the current run.
- Do not change source from this diagnosis alone. First inspect the independent fullTests result. If it fails, obtain one isolated trace with the existing test scenario that records actual `resumeRequests.count`, the event returned at line 295, `generationRuntimes[runID]?.terminalClaim` around the lease hop, and durable run status. This can be done in a disposable test copy after fullTests finishes; no main-repo test/assertion change is needed. An isolated pre-split single-case repetition is appropriate if Root wants to confirm the scheduling race on the original layout; keep its DerivedData separate.
- If confirmed, repair at the generation stream owner boundary: invalidate the old consumer's ownership when detach is claimed, and allow only the currently installed stream attempt to consume terminal/end callbacks. Preserve current `responseCursor`, partial content, sidecar, terminal-claim, and background lease ordering. A run ID alone or the mutable detached boolean cannot distinguish an old local stream from its foreground replacement. Avoid canceling the old consumer before the adapter closes its local stream: the adapter's cancellation hook can cancel the durable remote response.

## Validation scope after an authorized fix

Run this case with its late-detach and lease-hop neighbors in `NovelGenerationLifecycleTests`, then the relevant generation lifecycle/recovery suite. Keep build, simulator test, and real provider/background acceptance separate.
