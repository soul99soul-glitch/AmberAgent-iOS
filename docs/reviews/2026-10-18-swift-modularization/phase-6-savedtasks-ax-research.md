The smallest *proven public interaction workflow* is an `XCUIApplication` UI test that navigates the real app to `管理常用任务`, queries `XCUIElement`, taps, and checks the resulting state. Keep existing store/model unit tests and rendered PNG tests for their separate contracts. Do not convert the 12 failed interaction tests into skips or claim their assertions passed from screenshots.

Fresh reboot focused-r3 still has key/visible scene-backed `UIWindow` and rendered SwiftUI pixels, but the expanded unit-host tree contains 33 objects/0 labels for editor and 11 objects/0 labels for empty state. The original lookup fails before any `accessibilityActivate()` or business assertion. The fixtures and production SavedTasks view are unchanged from HEAD per `/tmp/amber-phase6-savedtasks-diagnosis.md`; that document also records the separate IntelligentUI interaction test's explicit AX-unavailable skip. Phone agent owns additional local fixture/scene-height probes. This research does not reproduce its diagnostics or assume an OS-wide regression.

## Search path and local public API check

Used `gh search issues` for `UIHostingController accessibilityElements SwiftUI`, `SwiftUI accessibility snapshot missing elements`, and project-specific SwiftUI accessibility issues; `gh search repos` for `accessibility-snapshot` and `ViewInspector`; `gh repo view`, README/source and issue comments for the candidates below. Cross-checked Apple developer documentation and read the installed UIKit headers. Subagents were skipped: this is one narrow iOS testing boundary and the Phone agent is already handling independent internal diagnosis. No private repositories, builds, tests, GUI, or dependencies were used.

The installed SDK's `UIKit.framework/Headers/UIAccessibilityContainer.h:31,60-65` declares `automationElements: [Any]?` on `NSObject (UIAccessibilityContainer)` (iOS 17+). Its comment describes children specifically for automation: when unset, it can fall back to `accessibilityElements`, identifier-bearing subviews, or an empty array. `UIAccessibility.h:44,285-287` separately declares `automationElementsBlock: AXArrayReturnBlock?` on `NSObject (UIAccessibility)` (iOS 17+). See [Apple UIAccessibilityContainer](https://developer.apple.com/documentation/uikit/uiaccessibilitycontainer) and [Apple `automationElementsBlock`](https://developer.apple.com/documentation/objectivec/nsobject-swift.class/automationelementsblock?changes=_9_3&language=objc). These are container/element APIs, **not** a documented way to request a full SwiftUI AX tree from a unit test. A temporary read of `automationElements` and node types/identifiers on the same failed host is a public diagnostic if the Phone agent's current probe leaves an ambiguity; it is not a fix and is unlikely to help if SwiftUI supplies no custom automation children. Do not set either property or invoke a block on production/test wrapper views to fabricate missing buttons.

## Recommended verification path

1. Let the Phone agent's single-case public fixture probe finish. If labels appear under `automationElements` or a changed scene height, make only that test-fixture adjustment, then rerun the exact failing action assertions. A node label alone does not prove `accessibilityActivate()` succeeds; verify state change. The mature library evidence does not support further blind AX traversal variants when the union is label-empty.
2. If the fresh unit host remains label-empty, preserve the failed result as an unmet unit-host interaction gate. Use the existing production `IOSPhoneControlSettingsView` `NavigationLink(value: Route.phoneSavedTasks)` with identifier `phoneControlSavedTasks` to enter the screen in a separate UI test. Apple documents [`XCUIApplication`](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication) as the app launch/control proxy and [`XCUIElement`](https://developer.apple.com/documentation/xcuiautomation/xcuielement) as the query/gesture element with `waitForExistence`, `hittable`, `tap`, and `typeText`. This exercises the installed app's automation tree and actual taps without a production state hook. Keep the UI scenario focused on an action that can be configured through the visible interface and compare the saved/list/error outcome; report any scenarios still blocked by data setup separately.
3. For accessible descriptions and hit regions, Apple supports [`XCUIApplication.performAccessibilityAudit`](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/performaccessibilityaudit%28for%3A_%3A%29) and [Accessibility Inspector audits](https://developer.apple.com/documentation/accessibility/performing-accessibility-audits-for-your-app). These are supplemental accessibility checks, not replacements for the SavedTasks action assertions. Pixel screenshots prove rendering only.

Do not introduce a production launch flag/seed hook, `UIAccessibilityElement` shadow tree, private SwiftUI/AX symbol, synthesized UIKit touch, exact-label broadening, fallback skip, or a new snapshot/reflection framework solely to turn the failing tests green. None has a verified causal link to the current zero-label result. If the app UI test also has no elements, that is new evidence to investigate production accessibility; the unit-host result by itself does not establish a production defect.
