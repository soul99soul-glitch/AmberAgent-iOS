## 1. 要解决的问题

用户经常需要在 agent 给出的几个方案之间做选择，补充约束，再让 agent 继续工作。目前这些选择主要通过文字表达。可视化 widget 能改善展示，其按钮也能触发下一轮，但这不等于系统已经理解或保存用户在界面中的选择。

本计划的目标是让一类明确的任务拥有合适的交互界面，并让用户操作成为可追溯的下一步输入：

> agent 提出有依据的选项 → 用户选择并补充约束 → 本地保存草稿 → 用户提交 → 一条带明确来源和选择快照的用户消息进入现有运行链路 → agent 基于该选择继续。

第一阶段以“方案比较与决策”为场景。完成标准是这条路径能够在生产聊天入口运行、恢复、复核，而不是生成更多图形或做出更丰富的动画。

## 2. 概念与产品边界

| 层次 | 职责 | 在本项目中的处理 |
| --- | --- | --- |
| 绘制与呈现 | 画出图形、图表、三维场景或页面 | SVG、Three.js、VChart、HTML 等继续服务于展示与独立产物 |
| 交互组件 | 接收选择、文字输入、展开等操作 | 采用现有视觉系统下的原生 SwiftUI 控件 |
| 任务界面 | 根据任务组织内容与控件，保存用户状态，形成明确的下一步输入 | 本计划新增的智能 UI 路径 |
| Agent 运行 | 推理、调用工具、审批、持久化消息、报告结果 | 复用现有聊天与 runtime；任务界面不能自建另一套执行链路 |

智能 UI 的判断标准是：界面是否围绕当前目标提供有用的操作，以及这些操作是否真正影响后续工作。可点击、会动、具有三维效果，都不是充分条件。

生成式 UI 与智能 UI 也不完全等同。前者描述界面的生成方式；后者强调任务适配和交互作用。第一阶段允许模型选择可靠的任务模板、填入内容，不要求模型生成任意布局或应用代码。

SVG、Three.js 可以成为任务界面中的呈现内容，但不能承担任务状态的唯一存储，也不能凭其内部点击直接取得 agent 工具权限。第一阶段无需把它们嵌入新任务卡。

## 3. 通用设计原则

### 3.1 先确定用户下一步需要做什么

生成界面前判断：用户是需要阅读结论、理解机制、比较选项，还是提供下一步所需的信息？只有重复选择、补充输入或探索参数能够显著降低操作成本时，才增加任务界面。

简单问答用文字，静态比较可以用表格，解释结构可以用图。不能把所有回答都升级成卡片，也不能因为有智能 UI 能力，就把本来已授权且可直接完成的任务变成等待用户选择。

### 3.2 本地交互与模型推理分别负责

选择选项、编辑字段、展开依据在本地响应，不调用模型。只有用户明确提交，或通过普通聊天要求继续时，才形成下一轮输入。

本地只执行宿主已实现的确定性逻辑。第一阶段不运行模型生成的 JavaScript、计算表达式或脚本；不把确定性控件行为包装成新的模型调用。

### 3.3 用户状态有明确所有者

模型拥有提案内容；宿主拥有用户的选择与草稿。后续生成不能以默认值覆盖用户输入。

区分草稿与已提交快照：草稿可以修改，已提交快照记录“该轮实际用了什么”。保存草稿不表示提交，更不表示授权外部操作。

### 3.4 界面操作必须能回到对话

提交内容包含任务、来源卡片、所选方案及补充约束。不能仅发送“继续”“方案 B”或“上一张 UI”，要求模型自行猜测指代。

用户通过文字引用当前卡片时，也应能看到本轮采用的上下文。不要持续把每个控件变化上传给模型，或者默默注入所有历史卡片。

### 3.5 事实、建议与结果分别表达

模型提出的建议必须按建议展示。价格、设备、构建状态等外部事实应保留来源；未来若接入工具数据，优先通过宿主引用结果字段，避免模型重新抄写。

“已选择”“已提交”“agent 正在处理”“工具已完成”“结果已验证”有不同含义。UI 不能用同一枚成功标记代替这些状态，也不能根据生成文案推断执行成功。

### 3.6 尊重现有任务与授权流程

第一阶段唯一提交动作是继续对话。卡片不直接调用安装、删除、付款、手机控制或其他工具。下一轮需要执行什么、是否需要审批，继续由现有 runtime 判断。

卡片文本、选项内容和输入都作为任务数据处理，不提升为 system/developer 指令。

## 5. 实现路径的比较与决定

| 路径 | 优势 | 成本与不足 | 判断 |
| --- | --- | --- | --- |
| 在 HTML／MiniApp 上增加状态回传 | 自由布局，复用 Web 运行设施 | 状态依赖页面生命周期，需要把页面逻辑、宿主事件、权限与任务来源再接起来；容易与视觉产物混淆 | 保留给独立应用场景 |
| 结构化任务描述＋原生固定模板 | 状态直接归宿主，支持无障碍，易沿现有发送路径验证；无需执行生成代码 | 初期只支持少量任务类型 | 第一阶段采用 |
| 自建 DIL 类语言、编译器与运行时 | 长期表达力与组合能力强 | 编译、流式修复、沙箱、状态 reconciliation、错误反馈都要建设；当前需求没有证明这笔成本合理 | 暂不采用 |

**决定：新增独立的 `task-ui` 正文协议，先提供一个“方案决策”模板。**

不新增 `show-widget` 的任务 renderer：当前视觉解析需要可渲染代码或预览，actions 也是固定文字。把任务卡塞进去会让视觉校验、预览导出与任务状态互相依赖。

可复用的只包括聊天正文的分段位置、稳定来源信息、现有控件视觉和运行入口。确有重复时再提取局部 fence 扫描逻辑，不为两个格式重写整个 Markdown parser。

## 6. 第一阶段的用户体验

试点任务：用户需要比较两至八种可行方案，并决定沿哪一种继续。

1. Agent 先取得必要事实，给出简短判断；若当前任务确实需要用户决策，输出一张任务卡。
2. 卡片展示当前目标、待决定的问题、方案内容和主要取舍。推荐项可以标注“推荐”，但不自动当作用户选择。
3. 用户选择一个方案，可填写与任务相关的补充字段，例如必须保留的能力、时间约束。卡片立即显示当前选择摘要。
4. 修改只更新本地草稿，不发消息，不触发工具。离开聊天、重新打开后恢复草稿。
5. 用户点击“基于选择继续”，宿主生成可见的用户消息，携带完整、简洁的选择快照，沿现有运行链路启动一轮。
6. 用户消息实际接受／持久化后，卡片显示对应提交记录；生成失败时展示现有错误并保留选择，用户可沿现有重试路径继续。

例：

> 任务：确定智能 UI 第一阶段实现路径。  
> 选择：原生任务卡。  
> 补充约束：保留现有 SVG／Three.js 路径；先支持方案选择和继续对话。  
> 请求：基于以上选择细化实施步骤。

首版只在用户明确要求比较／选择，或任务确有未决且必要的分歧时使用。自动识别更多任务类型放到试点通过以后；卡片不能成为强制审批步骤。

## 7. 协议与职责

### 7.1 模型输出：小型声明式任务描述

`task-ui` 使用带版本的 JSON。首版只需要这些语义：

| 字段 | 含义 |
| --- | --- |
| `version` | 首版为 1；未知版本不可执行 |
| `card_id` | 一条消息内的卡片标识，不是全局任务或会话 ID |
| `kind` | 首版只接受 `decision` |
| `goal`、`question` | 当前目标与待决问题 |
| `options` | 两至八个选项；稳定 id、标题、摘要、取舍；推荐标记只用于展示 |
| `fields` | 零至十六个具名输入字段；稳定 id、标签与必填语义 |
| `submit` | 展示标签；宿主支持的动作固定为 `continue` |

首版每条助手消息最多一张可操作任务卡。限制选项与输入规模是为了让试点保持一个清楚的决策，不是为后续创建通用表单框架。

模型不能声明会话 ID、消息节点 ID、工具名、宿主权限、任意回调代码或网络地址。字段值与选项文案都只作为内容。明确验证重复 id、缺失引用、必填项、长度和结构，验证失败时显示可理解的错误并保留正文，不擅自替用户修复选择。

### 7.2 宿主状态：一个按来源隔离的 owner

新增 iOS 侧任务状态 module，由会话级／App 级 owner 持有，卡片视图仅观察对应记录。不要只放在卡片 `@State` 或 WebView DOM 中。

来源 key 由宿主构造：`conversationID + sourceMessageID + textPartIdentity + cardID`。sourceMessageID 使用当前变体的 UIMessage UUID；MessageNode 可以包含多个变体，不能以 node.id 单独隔离。textPartIdentity 使用该消息的 partIndex，定义指纹变化时使旧草稿失效；不使用文本偏移或当前分支下标。

状态分为：

- 定义：已验证的任务描述和定义指纹，来自助手消息。
- 草稿：当前选择、输入值与本地修订号，来自用户操作。
- 提交快照：来源、修订号、所选内容、字段值和对应用户消息，冻结后不随草稿变化。
- 运行展示：通过对应用户轮次／run 的已有状态派生，不由卡片自行维护另一份运行状态。

采用单独的小型 iOS 持久化文件／记录，参考现有本地 store 的模式；不把每次输入变动写回整份 conversation，也不扩大 artifact shelf 的职责。保存与读取在事件或 owner 加载路径执行，SwiftUI body 不做磁盘 IO。

第一阶段承诺同一设备的草稿恢复。提交快照作为会话消息保留；本地草稿不承诺跨设备同步或通过会话备份恢复。导入／替换会话时，对来源不再存在的草稿停止绑定；删除会话时清理其状态，采用现有删除／导入生命周期，不另建后台清理系统。

### 7.3 提交 interface：状态快照进入已有聊天链路

用一个宿主提交入口完成来源校验、必填验证、重复提交控制和用户消息构造。视图提交语义请求，不拼接自由指令，也不暂存／覆盖 `inputText` 来模拟用户发送。

复用 `sendUserMessage` 等既有发送 seam；普通聊天草稿、待发送图片和文件上下文不被任务卡消费。卡片请求只携带自己的字段与来源，需要用户额外附加资料时仍走现有 composer。

可见用户消息中包含选择摘要；消息 metadata 保存机器可读的来源与快照。Provider 请求必须包含必要的语义文本，不能指望未上传的 metadata 会被模型理解。对应来源已被上下文裁剪时，仍能从该快照理解目标、选项和约束。

已提交用户消息是提交记录的 durable 依据。状态 store 不另建一份独立提交日志去竞争所有权；重启时可通过消息中的提交标识恢复关联。在消息被接受但尚未确认落盘时展示“提交中”，不能提前宣称 durable success。

第一阶段生成中允许修改草稿，但禁用提交并显示“当前回复结束后可提交”。不静默返回，不自动进入 steer，也不触发第二个并发 run。之后若确有中途转向需求，再独立评估与现有 steer 的整合。

同一卡片按钮提交中的重复点击只接受一次。已提交且草稿未变化时按钮不重复发送；草稿有变化后可明确再提交一轮。用户另发“按这个继续”等明确文字请求可以复用已提交选择，这是一条新的用户请求。失败后不自动重发用户消息或工具副作用，继续使用现有运行重试机制。

### 7.4 普通文字跟进

卡片按钮不是唯一入口。用户在 composer 输入“按这个继续”时，宿主可以携带当前活动任务卡的快照：

- 只匹配当前会话、当前分支中用户最近明确操作的有效卡片；不是全局最近的一张。
- 尚未选择／必填未完成时，提示补齐；存在无法唯一确定的指代时，保持文字路径并澄清对象，不能自行替用户选卡。
- 发送时冻结状态，不在运行中读取变化后的草稿。
- 消息展示中可见“采用了哪张卡、哪些输入”；普通问答不附带无关草稿。

“最近明确操作”是宿主记录的用户交互，不由模型生成的 card id 或推荐标记决定。


### 7.5 组件目录与自由度（用户追加要求）

用户明确要求七八十种组件及丰富样式，本轮交付规模确定为 **80 种真实原生组件**。它们是可组合的内容／控件，不是 80 个决策流程，也不通过颜色别名凑数量。

| 类别 | 数量 | 能力范围 |
| --- | --- | --- |
| 布局 | 10 | 行列、网格、卡片、分组、留白和分隔 |
| 文字 | 12 | 标题、正文、引用、代码、列表与键值 |
| 状态 | 10 | 标签、进度、通知、空态与提示 |
| 输入 | 14 | 单／多选、文字、数值、开关、日期、评分等 |
| 数据 | 10 | 指标、表格、比较、时间线、原生图表 |
| 媒体 | 8 | 图片、图标、头像、文件／链接摘要及结构图 |
| 任务内容 | 8 | 目标、上下文、依据、取舍、假设与选择摘要 |
| 操作与展开 | 8 | 提交／重置、按钮组、折叠、分页与菜单 |

根协议可包含 `components`。组件通过宿主目录 kind 与已声明的 fieldID 绑定，不运行任意代码；允许原生容器嵌套组合，移动端限制深度 8、节点 160，单卡 JSON 不超过 131,072 字节。样式使用有限设计 token（色调、强调程度、密度、对齐、间距），支持与 AmberTheme 一致的丰富组合。

所有输入都写入同一个草稿 owner；展开／tabs 等展示状态也由具名绑定恢复，但不作为用户任务约束上传。媒体／来源组件不凭生成内容宣称外部事实已验证。所有 continue/reset 控件仍进入统一宿主事件入口，不直接执行工具。

P0 先验证基础任务壳；P1打通持久化与提交；P2接入完整80组件和模型目录；P3逐类验证交互、布局与默认生产路径。最终验收包含80项目录唯一性、可构造／可渲染，以及具代表性的输入与组合实际交互，不用enum数量代替功能证据。

## 8. 模型指导与能力范围

在 iOS 请求准备路径提供独立的任务 UI 能力说明，与既有视觉输出指导并列。首版协议、任务壳与组件目录在 Swift 侧维护；通过当前 `Shared.framework` 消费既有 KMP 能力，不能假设有独立发布的 Core UI runtime。

能力说明必须明确：

- `show-widget` 是视觉产物，`task-ui` 是决策与继续任务的界面，两者用途不同。
- 任务壳首版为 `decision`；内部可组合 80 种已实现原生组件，不输出宿主尚未支持的控件或动作。
- 先取得事实，再提出选项；不以卡片代替工具调查或真实结果。
- 有充分信息和授权时直接推进，不人为插入决策卡。
- 用户要求纯文字、明确视觉产物或独立 MiniApp 时，尊重对应输出路径。

当前 `GenerativeUiPlanner` 的 PROSE 指导限制的是 widget，不能通过放宽它来让所有任务自动生成 UI。整合时检查 prompt 是否把任务卡误当视觉 widget，并确保 `widgetRequirement` 不把缺少任务卡当作视觉补绘失败。不新增自动修复轮次。

首版复用既有 Generative UI enabled／enableActions 的开关语义；关闭时不提供可操作任务卡。只在宿主确有 decoder、原生模板和提交入口时向模型声明能力。不为此新增一排实验设置；若后续产品需要独立控制视觉与任务界面，再另做设置契约。

本计划不直接修改共享 KMP 视觉协议。若实施中证明必须修改共享 prompt／settings，须说明原因，同时验证 Swift 消费入口与受影响 Gradle 测试；其他产品消费者的支持状态不在本次检查范围内。

## 9. 流式生成、历史与呈现

第一阶段不追求半截任务 JSON 可交互。正文按现有方式流式展示；任务块未完成时展示简短加载状态，完整且合法后可展示只读预览，来源助手轮次成功结束后才启用输入和提交。

取消、失败或 final snapshot 改写时，不把未确认定义变为可执行卡片。相同定义的重复投影不重置草稿；真正改写来源内容或改变字段结构时，使旧绑定失效并给出说明，不能按数组位置迁移用户选择。

后续回答默认追加新消息和新卡片。第一阶段不让模型实时改写已提交的旧卡片；旧卡保留来源和提交历史，不伪装成新的执行结果。

使用 AmberTheme 和已有原生控件，支持深浅色、动态字号、VoiceOver、键盘、安全区与 Reduce Motion。方案取舍先保证可读，长文本可展开，主要点击区域至少 44pt。任务卡的高度变化必须经过现有测量和 viewport 路径，用户查看历史时不能被强拉到底部。

首版无需把任务卡接入产物架。它是任务交互记录；未来需要在产物架中发现／回访时，再设计对应类型，不能以 HTMLPage 形式假装导出为可运行页面。

导出／旧客户端至少保留简短的目标、选项和已提交摘要。未知协议或无法恢复的草稿显示只读状态；可阅读不代表可以继续执行。实现时检查既有导出是否包含新增本地文件，避免误承诺草稿备份。

## 10. 实施阶段

阶段按依赖顺序实施；每阶段完成后由独立 subagent 核查逻辑闭环、生产调用链、会话隔离和 UI 对齐／间距／尺寸，修复确认问题后推进下一阶段。

实现位置按职责组织，以下为候选新增文件，均位于 `iosApp/iosApp/`，不新建 package 或跨平台 runtime：

| 候选位置 | 集中的职责 | 接入现有位置 |
| --- | --- | --- |
| `IOSIntelligentUIProtocol.swift` | v1 类型、解码与验证、任务块分段、模型能力说明 | `ChatAssistantMarkdownView`、`ChatGenerationSupport` |
| `IOSIntelligentUICard.swift` | 原生 decision 模板，展示草稿并发出语义事件 | 默认 timeline 的正文渲染 |
| `IOSIntelligentUIStateStore.swift` | 来源隔离、草稿更新、持久化与恢复 | 会话生命周期；不替代 conversation store |
| `ChatIntelligentUISupport.swift` | 冻结提交快照、构造可见用户输入、接入既有发送 seam | `ChatViewModel` 和对应消息构造路径 |

这些位置用于让维护者找到状态和副作用的所有者，不代表四套公共 interface。对外只暴露卡片读取／编辑与提交所需的最小入口；解码、快照格式和存储细节尽量留在各自 implementation 内。

### P0：协议与默认生产路径的固定样本

产出：`task-ui` v1 decoder／validator、一个原生 decision 模板，以及生产正文分段的接入。

先用固定样本沿 `NativeChatTimelineView → MessageBubbleView → ChatAssistantMarkdownView` 跑通；在输入快照／事件 seam 上测试，不等待真实模型表现来判断宿主能否工作。暂不增加实时脚本、数据绑定或新绘制库。

完成判据：普通文字和旧 widget 行为不变；完整、流式、取消、非法与未知版本样本有明确展示；新卡片在默认列表中可选择和填写。

### P1：草稿持久化与提交闭环

产出：按来源隔离的任务状态 module、宿主提交 interface、可见用户摘要与提交 metadata。

覆盖切会话、切分支、重新打开、草稿改动、提交失败与重复点击；保护普通 composer 草稿和附件。用受控 provider／runtime fixture 检查实际请求，证明选项和字段确实进入下一轮，而不仅是卡片自身状态正确。

完成判据：选择／填写本身没有模型调用；一次提交产生一条用户轮次；对应请求包含正确快照；原会话结果不会串入当前会话；重启后恢复草稿和已提交关联。

### P2：能力指导与文字继续

产出：80 种原生组件目录与组合渲染、设计 token、iOS 能力说明、任务卡适用策略、普通文字引用的快照附加。

复核与 SVG、Three.js、slides、MiniApp 及视觉补绘策略的关系。真实 provider 用一个配置明确的模型完成试点，不把单模型通过推广成所有 provider 兼容。

完成判据：用户能够通过按钮或“按这个继续”推进同一个任务；模型理解实际选择；简单文字问题保持简洁；绘图与 3D 请求仍走原呈现路径。

### P3：必要的回归与体验验收

产出：受影响自动检查、模拟器交互证据、真机试点记录，以及仅针对本次 diff 的一次可维护性审查。

修正审查中有依据的问题后，只重跑受影响检查。达到本计划验收标准后结束首版；不自动追加模板、任务系统或跨平台改造。

### 通过首版后才评估的方向

若试点证明“选择、补充、继续”有稳定价值，再选择一个真实需求扩展：第二种任务模板、工具结果字段引用、已知规则的本地参数计算，或任务卡在产物架中的回访。每个方向都需要独立场景和验收，不作为首版前置依赖。

## 11. 验证计划

优先测试用户可见行为与实际上传请求。可以有 decoder 定点测试，但不能用 schema 测试代替提交与会话隔离集成证据。

| 场景 | 必须取得的证据 |
| --- | --- |
| 选择与补充输入 | 控件立即变化；provider 调用数不增加 |
| 显式提交 | 用户消息及实际请求包含目标、来源、选择与字段；一轮只提交一次 |
| 普通文字继续 | 引用明确时携带正确快照；未选或指代不清时不猜 |
| Composer 草稿／附件 | 从卡片提交前后的输入文字、图片与文件待发送状态不被消费 |
| 会话与分支切换 | 同名 card id 不串状态；迟到事件不能写入另一会话；历史分支只读取自己的来源 |
| 恢复与存储错误 | 同设备重新打开恢复草稿；保存失败有反馈，不显示已保存；导入／删除不绑定过时来源 |
| 重复点击／生成中提交 | 不重复插入用户轮次；生成中明确禁用，既有 run 不被抢占 |
| 流式／错误／取消 | 未完成或失败定义不可提交；final snapshot 对齐；完整定义不会因重复投影重置 |
| 普通内容回归 | 文字、SVG、Three.js、VChart、slides、MiniApp 的既有入口仍可用 |
| 布局与无障碍 | 深浅色、长标签、大字号、VoiceOver、键盘；历史阅读不被自动拉走 |
| 真实 provider | 至少一次“模型生成任务卡 → 用户操作 → 下一轮正确使用选择”的完整记录 |
| 真机 | 键盘、触控、切会话及重新打开的实际操作证据，与模拟器结果分别报告 |

已有设施优先复用：`IOSGenerativeWidgetParserTests`／`IOSGenerativeWidgetPayloadDetectorTests`、`ChatSendDeferredGenerationTests`、`ChatViewModelConcurrentConversationTests`、`IOSConversationStoreTests`／`IOSConversationStoreBranchingTests`、`ChatMessageProjectionTests`，并在新提交 interface 加入对应行为测试。

触碰聊天正文、投影或布局时，遵守 `iosApp/AGENTS.md` 的最低门禁：

  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  -parallel-testing-enabled NO \
  -only-testing:iosAppTests/ChatSwiftUIStreamReplayTests \

## 12. 首版验收与停止条件

首版必须同时满足：

1. 模型提出一个真实决策任务，原生卡片可用，不依赖 SVG／Three.js 或生成脚本承担语义。
2. 用户操作在本地生效且草稿可恢复。
3. 明确提交或明确文字引用后，agent 收到完整、正确、可核对的选择快照。
4. 状态、请求与结果按会话／来源隔离，输入框草稿和附件保持正确。
5. 旧视觉能力及生产聊天滚动路径通过受影响回归。
6. 自动检查、构建、模拟器操作、真实 provider 和真机体验分别记录；未取得的证据仍列待验证，不用其他层通过替代。

未通过时只修复这条路径中的已证实问题。如果固定样本可用而真实模型频繁误选模板，应先调整适用策略与提示，不立即引入语言／编译器。若任务卡没有减少解释或输入成本，则收窄适用场景，不扩大组件数量来弥补。

## 13. 首版不做

- 代码型 UI DSL、编译器、表达式执行器或插件系统；允许有界原生组件组合。
- 为智能 UI 新增 SVG、Three.js、绘制依赖或迁移现有视觉代码。
- 卡片直接调用工具、扩展 MiniApp 宿主权限，或重写审批流程。
- 模型实时重排正在操作的卡片、跨卡片工作流图、自动多轮 agent 调度。
- 跨设备草稿同步、任意工具结果绑定、所有 provider 的兼容承诺。
- 将 iOS 首版迁往独立发布的 Core 制品，或读取／修改其他产品仓库。
- 删除旧路径、顺手重构脏工作树中的手机控制／Jev／Live Activity 改动。
