# Amber × Jev v2：把 Jev 放到它有优势的位置

日期：2026-09-30。依据：开源项目调研（fast-jev-compaction、DeerFlow jev-context、winnow、toolgate、Vercel eve 自动批准、jev-belay）与本仓库 Jev 集成的评估。

## 背景结论

- 公开实测延迟 p50 约 130–420 ms、p95 约 230–540 ms，随 state 增大；放在首字等关键路径上的判断，400 ms 等待预算下命中率不稳。
- Jev 在窄的分类/门控任务上与前沿模型相当，排序（大量 0.99 并列、批量变化改变排序）是弱项。
- 社区收敛出的高收益模式：确定性规则先行、Noul 阈值门控、只向安全方向收紧、放在不挡主路径或本就要付代价的时机、先摆事实再提问。

## 共同约束（继承既有契约）

- 每个新能力是独立用途：off = 零网络；shadow 只记指标不改行为；active 需固定模型版本。
- Jev 失败、超时、跳过一律回到现有行为；不引入 Jev 失败时的新阻塞。
- 已有用途（工具发现、记忆召回、上下文筛选、模型调度、意图路由、审批分诊、网页操作、脚本判断）行为不变。
- 推荐配置加入新用途的 shadow，以便积累样本。

## Phase 1：压缩保留（toolResultRetention）

**问题**：`IOSContextCompactionCoordinator.editPreparedContext` 对较早消息里可清除的工具结果（`safeToClearPreparedResult` 且 > 2,000 字）一刀切清空，模型需要时只能重读。

**做法**：
- 候选：可编辑、可清除、输出 > 2,000 字的已完成工具结果，且其后已有 assistant 消息（模型已对它作出反应）。数据范围：当前任务文本、工具输出、工具元数据（state 含工具名与参数摘要）。
- 时机：候选仍在"最近消息"保留窗口内时，后台（不阻塞请求）批量问 Jev 一道 Noul："这条结果的原文在后续任务中是否仍需要保留"。state 为对话大纲（用户消息、assistant 文本摘要、工具调用单行摘要）加候选结果首尾样本。
- 应用：结果按 conversationId + toolCallId + 输出哈希固定。等该结果移出保留窗口时：active 且判定保留（keep 概率 ≥ 0.7）→ 跳过"清空"（>16k 的仍按原规则截成 8k 预览，单条体积有界）；其余情况（未判定完、判定不保留、shadow）→ 现有清空行为，并固定，保证 prompt 前缀稳定。仍在窗口内时判断失败不固定，下次准备时重试。判定只存内存，App 重启后回到原有清空行为。
- 指标：shadow/active 都记录候选数与保留数（差异率 = 保留比例）。

**验收**：
- off 零网络；active 下判定保留的结果在移出窗口后保持原文，其余照旧清空。
- 未判定或失败时行为与现状一致，且之后不再翻转。
- 请求准备路径不等待 Jev。

## Phase 2：自动批准复核（autoApprovalGate）

**问题**：全局自动批准或高风险自动批准开启后，任何工具调用都直接执行，没有第二道判断。

**做法**：
- 位置：`ChatToolRuntime.executeWithCurrentExecutionPolicy` 分发前的唯一入口。
- 触发：自动批准实际生效，且工具类别为终端 / 工作区 / 网页操作 / 高级工具 / 搜索；静态元数据明确 `mutates == false` 的只读调用直接跳过。
- 提问：一次请求四道 Noul，分别是破坏性、外发数据、超出任务范围、用户是否明确要求此操作。state 为工具名、参数摘要（沿用审批分诊的脱敏与截断）、最近三条用户消息。
- 判定：任一风险 ≥ 0.8，且不属于"用户明确要求（≥ 0.8）且非外发"的情况 → 本次调用在关闭自动批准的执行策略下执行，由各分支弹出原有审批卡。只收紧、从不放行；失败回到自动批准。
- UI：审批卡上方显示一行"已暂停自动批准：疑似…"及命中的风险类别（与审批分诊标签同位置）。
- 指标：shadow 记录"本会收紧"的比例。

**实现要点与范围**（review 后确定）：
- 跳过规则：只有静态元数据同时满足 `mutates == false` 且风险为 normal 才跳过（终端类工具 mutates=false 但风险为 sensitive，必须复核）；只读检索工具、编排/交互类工具（`execNestedToolExclusions`，收紧快照会传给子运行）、已获会话或运行级授权的终端调用不复核。
- 收紧快照同时把逐能力的自动批准降为每次询问（仅限该能力提供此选项）。
- 覆盖前台 kernel、嵌套 exec（带真实用户消息作为上下文）与后台生成；后台没有审批卡，收紧后按原逻辑返回"需回到 App 确认"。
- 命令类参数放宽到单字段 600 字（仍脱敏），避免危险尾部被截断。
- 已知限制：`wm_run_goal` 内层动作被收紧时直接交还主模型（无审批卡）；recipe 步骤审批卡 id 为复合 id，不显示说明行；复核在工具执行前同步等待，最长为网络 deadline（1.2 s）。
- 推荐配置不包含本用途：shadow 也会外发工具参数，需用户自行开启。

**验收**：
- 高风险调用在 active 下弹出原有审批卡并显示原因；低风险与只读调用照常自动执行。
- 自动批准关闭时零网络；Jev 失败时照常自动执行。

## Phase 3：完成声明校验（completionCheck）

**问题**：Agent 在本轮改过工作区文件后，可能没有运行任何检查就宣称"已完成 / 已验证"。

**做法**：
- 事实先行（本地、零网络）：本轮（最后一条用户消息之后）存在成功的写入类工具调用（`workspace_file_write` / `edit` / `move`），且最后一次写入之后没有终端执行类工具运行过含 test、build、lint、check 等关键词的命令。不满足即不问 Jev。
- 提问：一次请求两道 Noul，分别是"最终回复是否宣称任务已完成"、"是否宣称已验证或测试通过"，state 为事实摘要加最终回复。
- 应用（用户在环）：任一概率 ≥ 0.8 时，在输入框上方显示一条提示（"本轮修改了文件，之后没有通过的检查"）和"让助手验证"按钮。点击后走正常发送流程，发一条请助手运行相关检查的消息；有草稿或附件时只把验证请求追加到草稿，由用户确认发送。提示只在触发它的回复仍是最后一条消息时显示（切回该会话仍可见）。
- 事实门细节：只改文档类文件（md、txt、csv 等）或内容未变的编辑不算；检查命令只认同步返回的终端命令（`terminal_execute`、`ios_shell_execute`）；只是在等子代理的前台让出不校验。
- 已知限制：后台运行与 exec 脚本内的嵌套调用不在事实范围内；关键词按词匹配偏宽（偏向不提示）。
- 为什么不自动续跑：续跑时历史以 assistant 的最终回复结尾，Claude 会把它当作预填充续写，而不是开启新的一轮；若改为插入隐藏的用户消息，又要改动持久化历史和多家 provider 的消息交替约束。用户在环既避开这两处，也让用户知道发生了什么。
- 挂载点：`onRunTerminal`（终态为 completed 时），不在运行关键路径上。
- 指标：Jev 判定需要提示的比例（差异率）。

**验收**：
- 事实门不满足时零网络。
- 满足且判定为未验证的完成声明时显示提示；点击后发送验证请求。
- off、shadow、失败时不显示提示。

## 不做

- 模型调度改为"任务分级"：需要新增"分级 → 模型"的配置界面，收益未经验证，本轮不做，现有模型调度保持 shadow。
- 删除旧的"上下文筛选"：它与压缩保留作用于不同消息（最新输出和已移出保留窗口的旧输出），保持原样由用户选择；删除需另行授权。

## 执行纪律

- 每个 phase 先写失败测试再实现；phase 完成后跑 Jev 全部套件与相关回归。
- 每个 phase 完成后由 review 子代理（Sonnet 5.5 + high）检查逻辑闭环、调用链与 UI 细节，按发现精准修复。
